Keys, certs, backups — the operational facts

Not fetched — there's no single doc section for this, so it's written here directly. If it drifts from the code, the code wins; file an issue.

  • There is no database and no server-side durable state. The only state that matters lives on Solana (public, immutable) and in key files on whoever's machine generated them. Nothing here is backed up by this project — that's the operator's job.
  • CI signing key (.oath/ci-key.json or wherever oath init put it): if it's lost, past records anchored by it still verify (they don't depend on the key file surviving), but nothing new can be anchored under that signer until you rotate to a new one and update OATH_SIGNER everywhere. Losing it is not catastrophic; losing it to an attacker is (see THREAT-MODEL.md).
  • Approver key (quorum ≥2 setups): same as above, kept off CI by design. If it's lost with no copy, quorum can never be met again for new builds until a replacement approver key is added everywhere --quorum/OATH_SIGNER is configured.
  • --program (on-chain records, experimental): the deployed program's upgrade authority is currently a single key (the CI key). Losing it means the program can no longer be upgraded, but existing on-chain records remain readable and valid either way.
  • Webhook TLS certificate: 825-day lifetime, generated fresh by install.sh/Helm, not auto-rotated. Re-run install.sh (or helm upgrade) before it expires, or every new Pod in the cluster gets refused (failurePolicy: Fail).
  • Devnet has no retention guarantee. Anything anchored there could in principle be pruned by a network reset; this has not happened to this project's own fixtures so far, but it is not a promise. Mainnet is the durable option and is supported, but not yet exercised in CI (README: Mainnet).
